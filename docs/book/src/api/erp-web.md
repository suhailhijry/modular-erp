# erp-web

What a module's HTTP surface is built from. Authorization extractors, the
problem+json shape, the JSON and query extractors that refuse in this API's
shape, paging, and the request-level messages.

**Depends on:** `erp-control`.
**Used by:** `erp-api` and every module.

## Why this is a crate of its own

A module ships its own routes. `sales::http::routes()` is a router the sales
crate owns and the composition root mounts. For that to be possible, the
furniture those routes are made of has to live *below* the modules: an extractor
a module cannot name is one it cannot use, and a module that reached up into
`erp-api` to get one would close a dependency cycle, because `erp-api` names
every module.

Nothing here knows what a ledger or an invoice is, and nothing here may. The
moment it does, this is a module.

## The extractors

Read a handler signature top to bottom and it tells you exactly what was checked
before the body ran.

```rust
async fn issue_invoice(
    tenant: Allowed<PostEntries>,          // member, and permitted to post
    State(state): State<AppState>,
    Language(locale): Language,            // Accept-Language, infallible
    Json(body): Json<NewInvoice>,          // parsed, or problem+json
) -> Result<(StatusCode, Json<Issued>), Problem> {
    require_module(&tenant, &crate::module_id(), locale)?;
    …
}
```

### Language

```rust
pub struct Language(pub Locale);
```

Infallible. An absent or unparseable header is English, not a 400. It is
extracted on its own so an error response can be localized even when the *next*
extractor is what failed.

### Authenticated

```rust
pub struct Authenticated { pub session: Session, pub token: String }
```

Proof that a live session presented a valid token. Not cached in process, unlike
every other entry-path lookup, because a stale membership for five seconds is
survivable and a stale logout is not. Redis is where a shared session cache lives
when a deployment has one.

### Tenant

```rust
pub struct Tenant { … }   // holds a TenantDb
```

A route into one tenant, with every access check already passed. **The extractor
is the authorization**: `ControlPlane::enter` refuses unless the identity is
active, the tenant is enterable, and a live membership joins them. A handler
taking this has been handed proof of all three, and cannot obtain a `TenantDb`
any other way.

Which tenant comes from the subdomain. `AppState::domain` is what it is a
subdomain of.

### Allowed

```rust
pub trait Capability { const CAPABILITY: erp_control::Capability; }

// generated by the `capability!` macro in extract.rs, one per variant
pub struct Read;
pub struct PostEntries;
pub struct ManageAccounts;
pub struct ManageTenant;

pub struct Allowed<C: Capability> { … }   // Derefs to Tenant
```

`Tenant` proves membership. `Allowed<C>` proves membership **and** that the role
on it permits `C`.

**Why this is a type and not a call.** A handler taking `Allowed<PostEntries>`
cannot be reached by a viewer, and cannot be written to skip the check, because
there is no other way to get one. The alternative,
`tenant.require(Capability::PostEntries)?` on the first line, fails by omission:
silent, security-relevant, and invisible in review. It is the same argument that
gave `TenantDb` no public constructor.

It derefs to `Tenant`, so a handler still reaches `.db` and everything else
without unwrapping anything.

Coverage is not left to inspection either. `every_role_against_every_endpoint` in
`erp-api` walks the matrix of role by endpoint and pins the count, so a new route
without an authorization row fails the build instead of shipping open.

## Json and Query

```rust
pub struct Json<T>(pub T);      // extractor and response type
pub struct Query<T>(pub T);
```

`axum::Json`'s rejection is `text/plain` with no `code`, so the one thing every
route promises, that every failure is `application/problem+json` with a stable
code, was untrue for the most common client mistake there is: sending the wrong
body. A client that always parses problem+json got a surprise on exactly the
request where it most needed the message.

These are the same thing with this API's rejection shape. Swap the import and
nothing else changes. The status codes are still axum's: 400 for JSON that does
not parse, 422 for JSON that parses into the wrong shape, 415 for a missing
content type.

## Problem

```rust
pub struct Problem { … }

impl Problem {
    pub fn new(status: StatusCode, message: &Message, locale: Locale,
               catalog: &dyn Catalog) -> Self;
    pub fn from_error(status: StatusCode, error: &dyn Localize, locale: Locale,
                      catalog: &dyn Catalog) -> Self;
}
impl IntoResponse for Problem { … }
```

RFC 9457 `application/problem+json`, plus two fields that make it usable by a
client that is not a person.

```json
{
  "type":   "https://errors.example.com/auth.invalid_credentials",
  "title":  "Bad Request",
  "status": 400,
  "code":   "auth.invalid_credentials",
  "detail": "بيانات تسجيل الدخول غير صحيحة. يُرجى المحاولة مرة أخرى.",
  "args":   {}
}
```

**`code` is what a client branches on.** `detail` is prose in whatever language
was asked for, and branching on it breaks the first time a translator improves a
sentence. `args` carries the message's typed arguments, so a client can render
its own sentence instead of ours.

## ApiError

```rust
pub enum ApiError {
    Auth(AuthError),
    Access(AccessError),
    Enqueue(EnqueueError),
    Append(AppendError),
    BadRequest(Message),
    NotFound(Message),
}

impl ApiError {
    pub fn status(&self) -> StatusCode;
    pub fn into_problem(self, locale: Locale, catalog: &dyn Catalog) -> Problem;
}
```

One enum, one `From` per source error, one `status()`. Deliberately not a trait:
mapping a domain failure onto HTTP is a decision about *this* API, and scattering
it across the crates that produce the errors is how two of them end up
disagreeing about whether a conflict is a 409 or a 422.

**The catalog is an argument** because `BadRequest` and `NotFound` carry a message
the caller chose, and only the caller knows which catalog can render it. This
used to render through a fixed one, which was fine while every caller lived in
the same crate. The moment modules started shipping their own routes,
`ledger.does_not_balance` came back to a client as the bare code with no sentence
in it.

## Catalogs

```rust
pub static REQUEST_CATALOG: StaticCatalog;   // this crate's own
pub static CATALOG: Composite = Composite::new(&[
    &REQUEST_CATALOG, &erp_control::CATALOG, &erp_eventlog::CATALOG,
]);
```

`CATALOG` renders everything an `ApiError` can carry, which is what makes
`into_problem` a complete function. Without it, half its inputs would degrade to
a bare code.

A module's own failures are not in it and cannot be, because they are declared
above. A module renders those through a composite of its own catalog and this
one, which is what every module's `http::problem_for` builds.
`erp_api::CATALOG` is the union of all of them, and `docs/ERRORS.md` is generated
from that.

The codes here are about the *request* and not the domain. A malformed currency
code or an unusable identifier is the API's business, because nothing downstream
ever saw the value: it did not parse.

## Wire helpers

```rust
pub struct Amount { /* minor: i64, currency: String */ }
impl Amount { pub fn parse(&self, locale: Locale) -> Result<Money, Problem>; }

pub fn metadata<C: Capability>(tenant: &Allowed<C>) -> Metadata;
pub fn parse_id(raw: &str, locale: Locale) -> Result<AggregateId, Problem>;
pub fn bad_request(code: MessageCode, arg: &str, value: &str, locale: Locale) -> Problem;
pub fn require_module(tenant: &Tenant, module: &ModuleId, locale: Locale)
    -> Result<(), Problem>;
```

`Amount` is minor units and an explicit currency, never a decimal string and
never a float. A client that sends `10.50` has already lost the argument about
how many decimal places the currency has.

`metadata` records who did it, which every event carries (L5). It is generic over
the capability because every write is behind a different one and they all deref
to the same `Tenant`.

`require_module` returns **404, not 403**. The route does not exist for this
tenant, and saying "forbidden" would tell them what they are not paying for in a
way a 404 does not.

## Paging

```rust
pub struct Paged<T> {
    pub items: Vec<T>,
    pub next: Option<String>,      // absent means the list ended
}
impl<T> Paged<T> {
    pub fn of<R>(page: erp_types::Page<R>, view: impl Fn(R) -> T) -> Self;
}

pub struct After { pub after: Option<String>, pub limit: Option<i64> }
impl After {
    pub fn limit(&self, default: i64, max: i64) -> i64;
    pub fn cursor(&self, locale: Locale) -> Result<Option<Cursor>, Problem>;
}
```

Every list in the API is shaped this way, because the alternative was a bare
array that stopped at 200 and said nothing.

A `limit` above the maximum is **clamped, never refused**. A caller asking for
more than the server will give wants as much as it will give. A limit
below one takes the default, because a request for nothing is never what anybody
means and comes from an uninitialised variable.

A cursor this build cannot read is **refused, not ignored**. Silently starting
from the top would hand a caller the first page again and look like the list
restarting.

## Reading your own write

```rust
pub struct Consistency(pub Option<LogPosition>);   // from ?consistent_after=

impl Consistency {
    pub async fn wait_for(self, db: &TenantDb, group: &str, locale: Locale)
        -> Result<(), Problem>;
}

pub async fn nudge(state: &AppState, tenant: TenantId);
```

Projections are driven by a worker, so a read taken immediately after a write can
legitimately not see it. That is the design, and L4 buys exactly-once by
decoupling them, but it makes the most common client pattern, submit a form and
refresh the list, look like the write failed.

Every write returns the log position it landed at. A client that cares passes it
back as `?consistent_after=<position>`, and the read waits for the projection to
reach it.

The alternatives are worse. *Reading the log directly* would mean every read
model has a second implementation that must agree with the first. *Writing
synchronously to the projection* is what L4 exists to avoid. *Serving stale and
saying nothing* is what this replaces.

`wait_for` returns immediately when no position was asked for, which is the
common case. When it gives up, the code is `request.not_caught_up` and the status
is 503.

**It does not usually wait at all**, because `nudge` is called after every write.
That asks the control plane to visit the tenant, so the worker picks it up within
its claim interval instead of waiting out the idle backoff. Without it, the
first write after a quiet period would wait up to thirty seconds, which is the
difference between this being a feature and a timeout.

## AppState

```rust
pub struct AppState {
    pub control: Arc<ControlPlane>,
    pub domain: Arc<str>,
    // sealing key, optional
}

impl AppState {
    pub fn new(control: Arc<ControlPlane>) -> Self;      // .localhost, for local work
    pub fn on(control: Arc<ControlPlane>, domain: &str) -> Self;
    pub fn sealing_with(self, sealing: SealingKey) -> Self;
}
```

`domain` is what tenants are subdomains of. It is configuration and not a
constant. It differs per deployment and, more to the point, per developer:
`acme.localhost` resolves without touching `/etc/hosts` in every browser and in
curl.

The sealing key is `None` when the deployment has not configured one, and then
anything that would store a secret **refuses**. Nothing is ever stored in the
clear. That is L6.
