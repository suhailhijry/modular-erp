# erp-types

The bottom of the workspace. Value types with no I/O, no async, and no database
access, so the crate compiles to WASM and a Rust frontend can share it. That is
the reason it is fussy about things a less isolated crate could be casual about:
these types are the contract, and the compiler is what checks it.

**Depends on:** nothing in the workspace.
**Used by:** every other crate.

Every type here has a private field and a fallible constructor, and validates on
`Deserialize` as well as on construction. A guarantee that only holds for values
built in Rust is not a guarantee in a system whose state arrives from an
append-only log written by older versions of itself.

## Identifiers

Four UUID newtypes, generated by `uuid_id!`. None of them converts to any of the
others.

| Type | What it identifies |
|---|---|
| `TenantId` | A tenant. The routing key for every database decision in the system |
| `IdentityId` | Something that can authenticate. Not a person and not a role |
| `MembershipId` | One `(identity, scope, role)` grant |
| `ProfileId` | A party in a tenant's domain: employee, client, supplier, contact |

All four share the same surface:

```rust
impl TenantId {
    pub fn new() -> Self;                        // fresh, time-ordered (UUIDv7)
    pub const fn from_uuid(inner: Uuid) -> Self;
    pub const fn as_uuid(&self) -> &Uuid;
    pub const fn into_uuid(self) -> Uuid;
}
// plus Display and FromStr
```

`new()` is deliberately not a `Default` impl. `Default` on an identifier lets
`#[derive(Default)]` on any containing struct silently mint real ids, and
identity is the routing key for tenant data.

```rust
use erp_types::TenantId;

let id = TenantId::new();
let text = id.to_string();
let back: TenantId = text.parse()?;
assert_eq!(id, back);
```

## Counters

Three of them, generated by `counter!`. They wrap `i64` and, like the ids, do
not convert to one another.

| Type | What it counts |
|---|---|
| `LogPosition` | Position in a tenant's event log. Contiguous, equal to commit order (L1) |
| `Sequence` | How many events one aggregate has applied |
| `SchemaVersion` | Which shape a stored payload is in, for the upcaster chain |

This distinction is not decoration. In the prototype both position and sequence
were `u64`, and the dead-letter path wrote a per-aggregate sequence into a column
keyed by global position. Unrelated events shared a retry counter and
dead-lettered each other. Here the two are different types with no conversion,
and that defect does not compile.

```rust
impl LogPosition {
    pub const ZERO: Self;                 // before any record exists
    pub const ONE: Self;
    pub fn new(value: i64) -> Result<Self, NegativeCounter>;
    pub const fn get(self) -> i64;
    pub const fn next(self) -> Self;      // saturating
    pub const fn distance_from(self, earlier: Self) -> u64;
}
```

`new` rejects negatives. Postgres `BIGINT` columns are signed but these
quantities never are, so a negative reaching a query is caught at the boundary.
`next` saturates. At `i64::MAX` the system has other problems, and silently
wrapping to a position that already exists should not be one of them.
`distance_from` is for lag metrics and nothing else. Never do arithmetic on
positions.

```rust
use erp_types::LogPosition;

let checkpoint = LogPosition::ZERO;
let head = LogPosition::new(4_182)?;
let lag = head.distance_from(checkpoint);   // 4182
```

## Validated strings

Five of them, generated by `validated_string!`. Each carries a maximum length
and a character rule, and enforces both on construction and on `Deserialize`.

| Type | Max | Rule | Example |
|---|---|---|---|
| `DomainName` | 64 | ASCII alphanumeric, `_`, `-`, `.` | `journal_entry` |
| `AggregateId` | 128 | same | `1000`, `2026-Q1` |
| `EventName` | 96 | same | `sales.invoice.issued` |
| `ModuleId` | 48 | lower case, starts with a letter, `_` only | `tax_sa` |
| `EffectKind` | 64 | ASCII alphanumeric, `_`, `-`, `.` | `email.send` |

`AggregateId` is a string and not a UUID because some aggregates are keyed by
natural identifiers. A chart-of-accounts code and a fiscal period label are both
better keys than a surrogate, and forcing them through one would mean a lookup
table for no benefit.

`ModuleId` has the narrower rule for a reason worth knowing. It used to accept
the same character set as the others, which meant `tax-sa` constructed fine,
passed every test that does not touch the control plane, and failed at the moment
a tenant enabled it, because `entitlement.module_id` in the control schema is
`^[a-z][a-z0-9_]{0,47}$`. The database refused what the type had allowed. Now the
type carries the rule the schema enforces, and a module id that cannot be stored
is one that cannot be built.

`EffectKind` is stored, so renaming one strands every effect already enqueued
under the old name.

```rust
impl DomainName {
    pub const MAX_LEN: usize;
    pub fn new(value: impl Into<String>) -> Result<Self, InvalidString>;
    pub fn as_str(&self) -> &str;
    pub fn into_string(self) -> String;
}
```

Modules wrap this in a private helper so the literals in their own source do not
each carry a `Result`. From [`modules/ledger/src/lib.rs:145`](https://github.com/suhailhijry/modular-erp/blob/main/modules/ledger/src/lib.rs):

```rust
pub(crate) fn name(literal: &'static str) -> EventName {
    EventName::new(literal).expect("event names in this crate are valid literals")
}
```

The `expect` is safe because `names_are_valid` in `tests/ledger.rs` builds every
literal in the crate. A malformed one fails the build, not a request.

## StreamId

Where an aggregate's events live.

```rust
pub struct StreamId {
    pub domain: DomainName,
    pub id: AggregateId,
}

impl StreamId {
    pub const fn new(domain: DomainName, id: AggregateId) -> Self;

// Display renders as "domain/id"
```

A struct and not two loose `&str` parameters, which is how the prototype passed
them and how they got transposed.

## Money

Integer minor units plus a runtime currency. Never floating point:
`float_arithmetic` is denied workspace-wide, and a ledger that rounds differently
on two machines is not a ledger.

```rust
pub struct CurrencyCode([u8; 3]);   // three ASCII uppercase bytes, Copy

impl CurrencyCode {
    pub fn new(code: &str) -> Result<Self, InvalidCurrency>;
    pub fn as_str(&self) -> &str;
    pub fn exponent(&self) -> u8;          // SAR/USD 2, JPY 0, KWD 3
    pub fn minor_per_major(&self) -> i64;  // 100, 1, 1000
}
```

Do not assume the exponent is 2. Formatting and rounding both depend on getting
it right, and the crate knows the answer.

```rust
pub struct Money { /* minor: i64, currency: CurrencyCode */ }

impl Money {
    pub const fn from_minor(minor: i64, currency: CurrencyCode) -> Self;
    pub const fn zero(currency: CurrencyCode) -> Self;
    pub const fn minor(self) -> i64;
    pub const fn currency(self) -> CurrencyCode;
    pub const fn is_zero(self) -> bool;
    pub const fn is_positive(self) -> bool;
    pub const fn is_negative(self) -> bool;

    pub fn checked_add(self, rhs: Self) -> Result<Self, MoneyError>;
    pub fn checked_sub(self, rhs: Self) -> Result<Self, MoneyError>;
    pub fn checked_neg(self) -> Result<Self, MoneyError>;
    pub fn checked_abs(self) -> Result<Self, MoneyError>;
    pub fn checked_mul_int(self, factor: i64) -> Result<Self, MoneyError>;
    pub fn checked_cmp(self, other: Self) -> Result<Ordering, MoneyError>;
    pub fn checked_sum<I>(items: I, currency: CurrencyCode) -> Result<Self, MoneyError>;
}
```

### Why there are no operators

`Money` implements no `Add`, `Sub`, `Neg`, `Sum` or `Ord`. An earlier design
sketched `Money<C: Currency>` so that adding SAR to USD would not compile, and
that is wrong for this system: currencies are tenant configuration, chosen at
runtime, so they cannot be type parameters.

The guarantee survives a different way. Every operation that could fail returns
`Result`, so a currency mismatch is something the caller handles. `PartialOrd` is
absent for the same reason: comparing two amounts in different currencies is
meaningless, and a silent `false` is worse than a `Result` somebody has to read.
Use `checked_cmp`.

There is no multiplication by a fraction or a percentage. Those need an explicit
rounding policy, and burying one in an operator is how ledgers drift by a halala
per line. Modules that need one write it out; see `sales::vat`.

`checked_sum` takes the currency as a parameter and does not infer it from the
first element, so an empty sequence yields `zero(currency)` instead of failing.
Summing no journal lines is legitimately zero.

From [`modules/sales/src/vat.rs:240`](https://github.com/suhailhijry/modular-erp/blob/main/modules/sales/src/vat.rs):

```rust
let net = Money::checked_sum(bands.iter().map(|b| b.net), currency)?;
let tax = Money::checked_sum(bands.iter().map(|b| b.tax), currency)?;
```

And a full round trip:

```rust
use erp_types::{CurrencyCode, Money};

let sar = CurrencyCode::new("SAR")?;
let line = Money::from_minor(11_500, sar);      // 115.00 SAR
let paid = Money::from_minor(5_000, sar);
let outstanding = line.checked_sub(paid)?;      // 65.00 SAR
assert!(outstanding.is_positive());

let usd = CurrencyCode::new("USD")?;
assert!(line.checked_add(Money::zero(usd)).is_err());  // MoneyError::CurrencyMismatch
```

## Paging

Keyset, and opaque.

```rust
pub struct Cursor(Vec<String>);
pub struct NotACursor;

impl Cursor {
    pub fn over(parts: &[&str]) -> Self;
    pub fn parts(&self) -> &[String];
    pub fn part(&self, index: usize) -> Option<&str>;
    pub fn decode(text: &str) -> Result<Self, NotACursor>;
}
// Display encodes it

pub struct Page<T> { /* items, next cursor */ }

impl<T> Page<T> {
    pub fn of(items: Vec<T>, limit: i64, cursor: impl Fn(&T) -> Cursor) -> Self;
    pub fn complete(items: Vec<T>) -> Self;
    pub fn len(&self) -> usize;
    pub fn is_empty(&self) -> bool;
}
```

### The bug this exists to stop

Every list in this system used to take a `limit` and return that many rows. A
tenant with 201 invoices saw 200 and was told nothing, and the response looked
exactly like a complete one. That is the worst shape a bug can have. It reads as
working software, and the missing row is only noticed when somebody reconciles a
total by hand.

`LIMIT … OFFSET …` would not have fixed it. Offset counts rows from the start on
every page, so page 40 of a busy tenant's invoices scans 8,000 rows to return
200, and it is wrong under concurrent writes: an invoice issued while somebody
pages shifts every later row by one, so a row can be skipped or seen twice.

Keyset paging asks for the rows after this one, using the same columns the list
is ordered by. It reads one index range whatever page it is on, and a row
inserted meanwhile cannot displace anything, because the position is a value and
not a count.

`Page::of` marks a page that fills its limit as possibly having more behind it.
Possibly and not certainly: knowing for certain means asking for `limit + 1`
rows, which costs a row on every page to save one empty request on the last. A
caller that follows cursors to the end gets one empty page, which every paging
client already handles.

The cursor is opaque because what it holds is the query's business. Today an
invoice cursor is a tax point and an id. The day a list is ordered differently it
is something else, and a client that had parsed the old one breaks.

From [`modules/sales/src/projections.rs:365`](https://github.com/suhailhijry/modular-erp/blob/main/modules/sales/src/projections.rs):

```rust
Page::of(items, limit, |invoice| {
    Cursor::over(&[&invoice.issued_on.to_rfc3339(), &invoice.id])
})
```

The parts are the ORDER BY columns, in order. The resuming query reads them back
with `part(0)` and `part(1)`. `part` returns `Option` because a cursor from an
older build may have fewer parts than this one expects, and that is a cursor to
refuse instead of guess at.

## NonEmpty

A list that cannot be empty. Head and tail, so `first()` returns `&T` and not
`Option<&T>`. A `Vec` with a private invariant would keep the guarantee in a
comment.

```rust
pub struct NonEmpty<T> { /* head: T, tail: Vec<T> */ }

impl<T> NonEmpty<T> {
    pub const fn singleton(head: T) -> Self;
    pub const fn new(head: T, tail: Vec<T>) -> Self;
    pub fn try_from_vec(items: Vec<T>) -> Result<Self, Empty>;
    pub const fn first(&self) -> &T;
    pub fn last(&self) -> &T;
    pub const fn len(&self) -> usize;
    pub const fn is_empty(&self) -> bool;   // always false
    pub fn push(&mut self, item: T);
    pub fn iter(&self) -> impl Iterator<Item = &T>;
    pub fn map<U, F: FnMut(&T) -> U>(&self, f: F) -> NonEmpty<U>;
    pub fn into_vec(self) -> Vec<T>;
}
```

**Nothing outside this crate uses it today.** It was written to retire "entry has
no lines" as a runtime error, and the ledger ended up needing a stronger
invariant than non-emptiness: `ledger::BalancedLines` requires at least two
lines, one currency, no zero line, and amounts that sum to zero. A type that
guarantees only the first of those would not have removed a single check.

It stays because the guarantee is real and cheap and the next module that needs
exactly this will not have to write it. If nothing has used it by the time the
booking modules land, delete it.

## Errors

Every construction failure in the crate, each carrying enough to say what
rejected the input. "Something was invalid" is not enough.

| Type | Raised by |
|---|---|
| `IdParseError` | `FromStr` on a UUID newtype |
| `NegativeCounter` | `LogPosition::new` and friends, on a negative |
| `InvalidString` | Any `validated_string!` constructor |
| `InvalidStringReason` | The detail inside `InvalidString`: too long, or a forbidden char with its index |
| `MoneyError` | Currency mismatch, or overflow |
| `InvalidCurrency` | `CurrencyCode::new` |
| `Empty` | `NonEmpty::try_from_vec` on an empty vec |
| `NotACursor` | `Cursor::decode` |

They carry the type name, so a failure deep in a deserialization tree says which
newtype rejected the input.

## Timestamp

```rust
pub type Timestamp = chrono::DateTime<chrono::Utc>;
```

Always UTC. Local time is a display concern, applied at query time, never stored.
